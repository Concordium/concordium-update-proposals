CIS-8004: Agent Registry
==============================

   :stub-columns: 1

   * - Created

   * - Draft

   * - Supported versions
     - | Smart contract version 1 (concordium-std v10+) with concordium-cis2

Abstract
========

A standard interface for an Agent Registry contract that records the identity
of autonomous software agents as transferable CIS-2 NFTs.

CIS-8004 is the Concordium implementation of the Identity Registry component
of `ERC-8004 v2 (Trustless Agents) <https://eips.ethereum.org/EIPS/eip-8004>`_.
The Reputation Registry and Validation Registry components of ERC-8004 v2 are
out of scope for this version.

Each agent is identified on chain by a 64-bit token id. The canonical
off-chain identifier is the CIS-2 token address (Base58Check encoding of
``(version=0x02, ULEB128(index), ULEB128(subindex), TokenIdU64 bytes)``).

Each agent record carries an optional ``external_reference`` that points
either at a :ref:`CIS-8` cryptographic-key binding or at an external-identifier
binding (the ``Cis10`` variant of the union — see
:ref:`CIS-8004-CrossContractVerification` for current deployment status).


Introduction
============

CIS-8004 is the on-chain registry that mints a CIS-2 NFT for each agent and
records:

- A pointer to the agent's off-chain card (``agent_uri`` + ``metadata_hash``).
- An optional ``external_reference`` proving control of an off-chain identity.
- A payment-routing field (``agent_wallet``) with its own independent
  lifecycle from CIS-2 ownership.
- An open key/value metadata map.

CIS-8004 mirrors ERC-8004's Identity Registry as closely as Concordium chain
semantics allow. Section :ref:`CIS-8004-DeparturesFromERC8004` summarises the
deliberate differences.

Terminology and Conventions
---------------------------

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be
interpreted as described in :rfc:`2119`.

Relationship to Other CIS Standards
-----------------------------------

- :ref:`CIS-0` — CIS-8004 contracts MUST advertise support for ``CIS-0``,
  ``CIS-2``, and ``CIS-8004``.
- :ref:`CIS-2` — CIS-8004 agent NFTs are CIS-2 tokens. CIS-2 transfer,
  balance, operator, and token-metadata entrypoints are inherited; the
  transfer entrypoint additionally runs two CIS-8004 reset hooks (see
  :ref:`CIS-8004-Transfer`).
- :ref:`CIS-8` — Agents MAY carry a ``external_reference`` of variant
  ``Cis8(_)`` pointing at a CIS-8 cryptographic-key registration. The
  CIS-8004 contract verifies the binding at mint time via a cross-contract
  ``ownerOfKey`` call.

Common Types

.. _CIS-8004-AgentTokenId:

AgentTokenId
^^^^^^^^^^^^

.. code-block:: rust

    pub type AgentTokenId = TokenIdU64;
    pub type AgentTokenAmount = TokenAmountU8;  // always 1 for NFTs

``AgentTokenId`` uses the standard CIS-2 ``TokenIdU64`` wire form
(``[u8 length=8][8 LE bytes]``, 9 bytes total) on every entrypoint —
both CIS-8004-native (``agentOf``, ``setAgentURI``, …) and CIS-2 inherited
(``transfer``, ``balanceOf``, ``tokenMetadata``). See
:ref:`CIS-8004-TokenIdWireFormat`.

.. _CIS-8004-ExternalIdentifier:

ExternalIdentifier
^^^^^^^^^^^^^^^^^^

For verifier-anchored external-identifier bindings (e.g. social-media

.. code-block:: rust

   The field name is ``identifier_type``, not ``id_type``. Schema-driven

.. _CIS-8004-ExternalRefKind:

ExternalRefKind
^^^^^^^^^^^^^^^

.. _CIS-8004-AgentRecord:

AgentRecord (on-chain)
^^^^^^^^^^^^^^^^^^^^^^

.. code-block:: rust

    #[derive(Serial, DeserialWithState, Clone)]
    #[concordium(state_parameter = "S")]
    pub struct AgentRecord<S: HasStateApi> {
        pub agent_uri:          Option<String>,
        pub metadata_hash:      Option<[u8; 32]>,
        pub external_reference: Option<ExternalReference>,
        pub agent_wallet:       Option<AccountAddress>,
        pub status:             AgentStatus,
        pub registered_at:      Timestamp,
        pub revoked_at:         Option<Timestamp>,
        pub revocation_reason:  Option<String>,
        pub on_chain_metadata:  StateMap<String, Vec<u8>, S>,
    }

The ``owner_account`` is **not stored** on the record; it is derived from the
CIS-2 ownership state (``cis2_state.token_owner(token_id)``) at query time.

The ``agent_wallet`` **is** stored. It has an independent lifecycle from
CIS-2 ownership: initialised to ``Some(sender)`` on register, updated via
:ref:`CIS-8004-setAgentWallet` with cryptographic proof, and reset to ``None``
on every CIS-2 transfer.

.. _CIS-8004-TokenIdWireFormat:

Token ID Wire Format
--------------------

This section is normative. ``AgentTokenId`` is an alias for
``concordium_cis2::TokenIdU64``, with the on-the-wire encoding
``[u8 length=8][8 LE bytes]`` (9 bytes total). Every CIS-8004 entrypoint
that takes a ``token_id`` parameter — both CIS-8004-native
(``agentOf``, ``setAgentURI``, ``setExternalReference``, ``setAgentWallet``,
``getAgentWallet``, ``setMetadata``, ``getMetadata``, ``revoke``) and CIS-2
inherited (``transfer``, ``balanceOf``, ``tokenMetadata``) — MUST use this
single wire form. Schema-driven JSON renders it as a hex string of 16
characters (e.g. ``"0a00000000000000"`` for ``token_id = 10``).

Event payloads carrying a ``token_id`` field MUST use the same
``TokenIdU64`` wire form: CIS-8004-native events (tags 240..247) and CIS-2
inherited events (tags 251..255) are byte-compatible on the ``token_id``
field. From one ``register`` transaction the same bytes appear in both
events:

::

    fe 08 0a00000000000000 ...   ← tag 254 (CIS-2 Mint)
    f0 08 0a00000000000000 ...   ← tag 240 (CIS-8004 Registered)


Contract State
--------------

.. code-block:: rust

    #[derive(Serial, DeserialWithState)]
    #[concordium(state_parameter = "S")]
    pub struct State<S: HasStateApi> {
        /// Init-time dependency contract addresses.
        pub cis8_contract:  ContractAddress,
        pub cis10_contract: ContractAddress,
        /// Single-account admin (see Admin section).
        pub admin: Option<AccountAddress>,

        /// Agent records keyed by token_id.
        pub agents: StateMap<AgentTokenId, AgentRecord<S>, S>,

        /// Reverse lookup: (namespace, identifier-or-public-key bytes) -> token_id.
        pub refs_index: StateMap<(String, Vec<u8>), AgentTokenId, S>,

        /// Next token_id to assign.
        pub next_token_id: u64,

        /// CIS-2 ownership / operator state.
        pub cis2_state: Cis2State<AgentTokenId, AgentTokenAmount, S>,
    }

A token_id MUST appear in ``refs_index`` if and only if its agent record has
an ``Active`` status and a ``Some`` ``external_reference``. ``revoke`` and
the transfer hook (:ref:`CIS-8004-Transfer`) MUST release the index entry.


.. _CIS-8004-CrossContractVerification:

Cross-Contract Verification
---------------------------

When ``register`` or ``setExternalReference`` is called with a ``Some``
``external_reference``, the contract MUST:

1. Validate that ``ext_ref.contract_address`` matches the init-time-stored
   dependency address for ``ext_ref.kind``:

   - ``Cis8(_)`` ⇒ ``state.cis8_contract``
   - ``Cis10(_)`` ⇒ ``state.cis10_contract``

   On mismatch, reject with :ref:`CIS-8004-InvalidExternalReference`.

2. Dispatch on ``ext_ref.kind`` and invoke the dependency contract's view
   entrypoint read-only:

   - ``Cis8(key)`` ⇒ call ``CIS-8.ownerOfKey({ external_key: key })``;
     require the result to be ``Some(Registration)`` with
     ``status = Active`` and ``owner = ctx.sender()``.
   - ``Cis10(id)`` ⇒ call ``CIS-10.assertionFor({ external_identifier: id
     })``; require the result to be ``Some(Assertion)`` with
     ``status = Active`` and ``bound_account = ctx.sender()``.

   Any failure (invoke error, ``None`` return, wrong status, wrong owner)
   MUST be wrapped into :ref:`CIS-8004-InvalidExternalReference`.

3. Check uniqueness in ``refs_index``; reject with
   :ref:`CIS-8004-ExternalReferenceTaken` if the binding is already held by
   another agent.

.. note::

   The ``Cis10`` variant requires a deployed companion contract exposing
   ``assertionFor`` with the expected return shape. Deployments without a
   CIS-10 companion MUST reject every ``Cis10`` external reference at
   :ref:`CIS-8004-InvalidExternalReference`.

   The init-time-stored dependency addresses are not immutable. The admin
   MAY re-point them via :ref:`CIS-8004-setExternalRegistries` — useful
   when either CIS-8 or CIS-10 is independently redeployed. Implementations
   SHOULD provide read-only ``getCis8Contract`` and ``getCis10Contract``
   view entrypoints so integrators can sanity-check the currently-configured
   dependency addresses; see :ref:`CIS-8004-DeploymentStatus`.


Entrypoints
-----------

.. _CIS-8004-init:

init
^^^^

.. code-block:: rust

    #[derive(Serialize, SchemaType)]
    pub struct InitParams {
        pub admin:          AccountAddress,
        pub cis8_contract:  ContractAddress,
        pub cis10_contract: ContractAddress,
    }

Initialises:

- ``state.admin = Some(params.admin)``
- ``state.cis8_contract = params.cis8_contract``
- ``state.cis10_contract = params.cis10_contract``
- ``state.next_token_id = 1``
- Empty ``agents``, ``refs_index``, and ``cis2_state``.

.. _CIS-8004-register:

register
^^^^^^^^

.. code-block:: rust

    #[derive(Serialize, SchemaType)]
    pub struct RegisterParams {
        pub agent_uri:          Option<String>,
        pub metadata_hash:      Option<[u8; 32]>,
        pub external_reference: Option<ExternalReference>,
        pub initial_metadata:   Vec<MetadataEntry>,
    }

Authorisation
    The sender MUST be an account (``Address::Account(_)``). Contract
    callers MUST be rejected with :ref:`CIS-8004-Unauthorized`.

Validation
    The contract MUST:

    1. Validate ``agent_uri`` length ≤ 4096 bytes (allows ``data:`` URIs).
    2. Validate every ``initial_metadata`` entry per
       :ref:`CIS-8004-MetadataEntry`. Reject any entry with
       ``key == "agentWallet"`` with :ref:`CIS-8004-ReservedKey`.
    3. If ``external_reference`` is ``Some``, perform cross-contract
       verification per :ref:`CIS-8004-CrossContractVerification`.

Effect
    Assign ``token_id = state.next_token_id``; increment the counter. Mint
    one CIS-2 NFT to the sender (emits CIS-2 ``Mint``). Insert the
    ``AgentRecord`` with ``status = Active``, ``agent_wallet =
    Some(sender)``, ``registered_at = ctx.metadata().slot_time()``, and
    each ``initial_metadata`` entry inserted into ``on_chain_metadata``.
    If ``external_reference`` is ``Some``, insert the corresponding
    ``refs_index`` entry. Emit :ref:`CIS-8004-Registered`.

Return
    ``AgentTokenId`` (the newly minted token id).

.. _CIS-8004-setAgentURI:

setAgentURI
^^^^^^^^^^^

.. code-block:: rust

    #[derive(Serialize, SchemaType)]
    pub struct SetAgentURIParams {
        pub token_id:      AgentTokenId,
        pub agent_uri:     Option<String>,
        pub metadata_hash: Option<[u8; 32]>,
    }

Authorisation
    Sender MUST equal the current CIS-2 token owner; otherwise reject with
    :ref:`CIS-8004-Unauthorized`.

Validation
    Reject if the agent is ``Revoked`` with :ref:`CIS-8004-AgentRevoked`.
    Validate ``agent_uri`` length per :ref:`CIS-8004-register`.

Effect
    Replace ``agent_uri`` and ``metadata_hash`` (each ``Some`` value
    replaces; ``None`` MAY be a documented "leave unchanged" or
    "clear" semantic — implementations MUST pick one and document it).
    Emit :ref:`CIS-8004-URIUpdated`.

.. _CIS-8004-setExternalReference:

setExternalReference
^^^^^^^^^^^^^^^^^^^^

.. code-block:: rust

    #[derive(Serialize, SchemaType)]
    pub struct SetExternalReferenceParams {
        pub token_id:           AgentTokenId,
        pub external_reference: Option<ExternalReference>,
    }

Authorisation
    Sender MUST equal the current CIS-2 owner. Reject if the agent is
    ``Revoked`` with :ref:`CIS-8004-AgentRevoked`.

Effect
    If ``external_reference`` is ``Some``, perform cross-contract
    verification per :ref:`CIS-8004-CrossContractVerification` and check
    ``refs_index`` uniqueness. Release any previous ``refs_index`` entry,
    set the new value, and insert the new index entry. Emit
    :ref:`CIS-8004-ExternalReferenceSet`.

.. _CIS-8004-setAgentWallet:

setAgentWallet
^^^^^^^^^^^^^^

.. code-block:: rust

    #[derive(Serialize, SchemaType)]
    pub struct SetAgentWalletParams {
        pub token_id:   AgentTokenId,
        pub new_wallet: AccountAddress,
        pub deadline:   Timestamp,
        pub signature:  Vec<u8>,         // flat byte array
    }

Authorisation (dual)
    Both of the following MUST hold:

    1. ``ctx.sender()`` equals the current CIS-2 token owner; otherwise
       reject with :ref:`CIS-8004-Unauthorized`.
    2. ``signature`` verifies against ``new_wallet``'s on-chain
       credentials over the :ref:`CIS-8004-SetAgentWallet-CanonicalMessage`
       bytes; otherwise reject with
       :ref:`CIS-8004-InvalidAgentWalletProof`.

Validation
    Reject if the agent is ``Revoked`` (:ref:`CIS-8004-AgentRevoked`).
    Reject if ``ctx.metadata().slot_time() > deadline``
    (:ref:`CIS-8004-AgentWalletDeadlinePassed`).

Effect
    Set ``agent_wallet = Some(new_wallet)``. Emit
    :ref:`CIS-8004-AgentWalletSet` with ``new_wallet = Some(new_wallet)``.

.. _CIS-8004-SetAgentWallet-CanonicalMessage:

setAgentWallet — canonical signed message
"""""""""""""""""""""""""""""""""""""""""

The contract reconstructs the exact bytes the off-chain signer signed and
verifies the signature against them. The off-chain signer MUST produce these
bytes verbatim.

.. code-block:: rust

    fn set_agent_wallet_signing_bytes(
        token_id:         AgentTokenId,
        new_wallet:       AccountAddress,
        deadline:         Timestamp,
        contract_address: ContractAddress,
        genesis_hash:     HashSha2256,
    ) -> Vec<u8> {
        let mut bytes = Vec::new();
        bytes.extend_from_slice(b"CIS-8004/v1/setAgentWallet");  // 26 bytes UTF-8
        token_id.serial(&mut bytes).expect("ser");                // 8 bytes
        new_wallet.serial(&mut bytes).expect("ser");              // 32 bytes
        deadline.serial(&mut bytes).expect("ser");                // 8 bytes
        contract_address.serial(&mut bytes).expect("ser");        // 16 bytes
        bytes.extend_from_slice(genesis_hash.as_ref());           // 32 bytes
        bytes
    }

Total payload size: 122 bytes. The 26-byte UTF-8 prefix provides
domain separation; ``contract_address`` and ``genesis_hash`` pin the
signature to a single contract instance on a single network.

The contract MUST retrieve ``contract_address`` via ``ctx.self_address()``
and ``genesis_hash`` via ``ctx.metadata().genesis_hash()``. Neither value
may be supplied as a parameter.

.. _CIS-8004-revoke:

revoke
^^^^^^

.. code-block:: rust

    #[derive(Serialize, SchemaType)]
    pub struct RevokeParams {
        pub token_id: AgentTokenId,

Authorisation
    Sender MUST equal the current CIS-2 owner.

Effect
    Set ``status = Revoked``, ``revoked_at = Some(now)``,

.. _CIS-8004-Transfer:

transfer (CIS-2) — dual-reset hook
----------------------------------

The CIS-2 ``transfer`` entrypoint MUST run two CIS-8004-specific hooks in
addition to the standard CIS-2 ownership move:

1. **Clear ``external_reference``.** If the agent had a ``Some``
   ``external_reference``, set it to ``None`` and release the
   ``refs_index`` entry. Emit
   :ref:`CIS-8004-ExternalReferenceSet` with ``external_reference = None``.

2. **Reset ``agent_wallet``.** If the agent had a ``Some`` ``agent_wallet``,
   set it to ``None``. Emit :ref:`CIS-8004-AgentWalletSet` with
   ``new_wallet = None``.

Both reset events MUST be emitted before the standard CIS-2 ``Transfer``
event for the same token. The new owner MUST re-establish
``external_reference`` via :ref:`CIS-8004-setExternalReference` and
``agent_wallet`` via :ref:`CIS-8004-setAgentWallet` if they want the agent
to be re-bound and re-payable.

The remaining CIS-2 entrypoints (``balanceOf``, ``operatorOf``,
``updateOperator``, ``tokenMetadata``) follow the standard
:ref:`CIS-2` semantics with no CIS-8004-specific augmentation.
``tokenMetadata(token_id)`` MUST return the agent's ``agent_uri`` as the
CIS-2 ``MetadataUrl.url``.


supports
--------

A CIS-8004 contract MUST implement :ref:`CIS-0` and MUST return ``Support``
for ``CIS-0``, ``CIS-2``, and ``CIS-8004``.

.. _CIS-8004-Admin:

Admin and Upgradeability
------------------------

The contract supports upgradeability via Concordium's native ``host.upgrade``
primitive under a single-account admin model. Semantics are identical to
:ref:`CIS-8-Admin`: ``upgrade``, ``transferAdmin``, ``getAdmin``
entrypoints with reject codes :ref:`CIS-8004-NotAdmin` and
:ref:`CIS-8004-UpgradeFailed`, events ``Upgraded`` (tag 246) and
``AdminTransferred`` (tag 247).

Renouncing the admin (``transferAdmin`` with ``new_admin = None``) is
irreversible and permanently locks the contract against further upgrades
*and* against further calls to :ref:`CIS-8004-setExternalRegistries`.

.. _CIS-8004-setExternalRegistries:

setExternalRegistries
^^^^^^^^^^^^^^^^^^^^^

.. code-block:: rust

    #[derive(Serialize, SchemaType)]
    pub struct SetExternalRegistriesParams {
        pub cis8_contract:  ContractAddress,
        pub cis10_contract: ContractAddress,
    }

Authorisation
    Sender MUST equal ``state.admin``; otherwise reject with
    :ref:`CIS-8004-NotAdmin`.

Effect
    Atomically replace ``state.cis8_contract`` and ``state.cis10_contract``
    with the supplied values. After this call all subsequent
    :ref:`CIS-8004-CrossContractVerification` checks dispatch against the
    new addresses.

    Both fields MUST be supplied — there is no "leave unchanged" semantic.
    Callers wishing to update only one side MUST pass the current value
    for the other.

    The contract does NOT validate that the supplied addresses host
    contracts of the expected standards; standard detection is the admin's
    responsibility off-chain. A misconfigured address will surface as
    :ref:`CIS-8004-InvalidExternalReference` on subsequent ``register`` /
    ``setExternalReference`` calls.

Rationale
    Both ``cis8_contract`` and ``cis10_contract`` are pinned at
    initialisation. Because the CIS-8 and CIS-10 companion contracts may
    each be redeployed (bug fixes, upgrades) independently of CIS-8004,
    the admin needs a way to re-point the CIS-8004 instance at the new
    dependency address(es) without redeploying CIS-8004 itself.

A CIS-8004 contract module MUST embed its Concordium schema in the compiled

.. _CIS-8004-DeparturesFromERC8004:

Departures from ERC-8004 v2
===========================

This section is informative.

- **CIS-8004 has native ``revoke``.** ERC-8004 v2 has no native revocation
  primitive; CIS-8004 provides one because soft-deactivation without
  burning the NFT is the more common Concordium-ecosystem need.
- **``agent_wallet`` resets on transfer.** The new owner MUST explicitly
  re-establish ``agent_wallet`` via :ref:`CIS-8004-setAgentWallet`. This
  mirrors ERC-8004 v2 semantics.
- **``external_reference`` resets on transfer.** The new owner MUST
  re-establish their own ``external_reference``; previous bindings are
  released from ``refs_index``. This is stricter than the ERC-8004 v2
  spec, which is silent on the question.
- **Identifier form is CIS-2 token address (Base58Check), not URI/DID.**
  Off-chain consumers receive a single canonical Base58Check string
  derived from ``(contract, token_id)``.
- **Reputation Registry and Validation Registry** components of
  ERC-8004 v2 are out of scope for this version.

Security Considerations
=======================

Dual authorisation on ``setAgentWallet``
    Both the current owner AND the new wallet's controller must
    authorise — protecting against either side unilaterally redirecting
    payments. The 26-byte ``CIS-8004/v1/setAgentWallet`` prefix and the
    ``contract_address`` + ``genesis_hash`` pinning prevent cross-context
    signature replay.

Transfer hook resets
    Both ``external_reference`` and ``agent_wallet`` are reset on every
    transfer. This prevents a previous owner's payment address or external
    identity binding from accidentally persisting under new ownership. The
    new owner MUST explicitly re-establish each.

Admin powers
    The admin can replace the contract code via ``upgrade``. Deployers
    SHOULD use a multi-credential Concordium account so admin actions
    require multi-party authorisation at the account layer. Renouncing
    admin (``transferAdmin`` with ``None``) is irreversible.

CIS-2 contract recipients
    ``transfer.to`` MAY be a contract address per CIS-2. Implementations
    SHOULD consider whether contract-owned agents are meaningful for their
    use case — agent NFTs held by a contract have no direct CIS-2
    ``signature`` channel for re-setting ``agent_wallet``, so the agent
    would be unable to receive payments routed through that field until
    transferred back to an account.
